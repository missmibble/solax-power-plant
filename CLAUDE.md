# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

An AWS CDK app (JavaScript CDK v2), deployed and live: three stacks, seven Lambdas implemented (not stubs), plus a dashboard. `PollerFunction` polls the real SolaX Cloud API (Inverter device, plus an auto-discovered Battery device) and writes to DynamoDB; `DashboardApiFunction` serves cost-aware rollups including battery charge/discharge/SOC when available, plus the latest nightly report (recommendation + optional AI narrative) and the latest weather/charge decision; `AlertFunction` reacts to the DynamoDB Stream and checks for import anomalies and real inverter fault codes; `ReportFunction` runs nightly and publishes a usage + battery-recommendation report, SOC-aware when battery data is present, plus an optional Bedrock-generated narrative and pattern-based anomaly flags layered on top of the deterministic recommendation — and persists the same data for the dashboard to read; `BatteryControlFunction` checks tomorrow's weather forecast nightly and adjusts the inverter's grid-charge target accordingly — dry-run by default, see [docs/battery-charge-logic.md](docs/battery-charge-logic.md) before ever enabling it live — and persists its decision for the dashboard too; `GridDischargeFunction` discharges surplus battery capacity to the grid during a premium 5-9pm feed-in window, calculated from historical shoulder-night usage — dry-run by default, see [docs/grid-discharge-logic.md](docs/grid-discharge-logic.md) before ever enabling it live; `SettingsOptimizerFunction` runs weekly and asks Bedrock whether the hardcoded battery-charge and grid-discharge defaults should be adjusted, based on a week of the other two functions' own decision history — recommendation-only by default, see [docs/settings-optimizer-logic.md](docs/settings-optimizer-logic.md) before ever enabling `autoApply`. Both SNS topics (`powerplant-alerts`, `powerplant-reports`) have a confirmed email subscription. A static dashboard (`dashboard/`), served via S3 + CloudFront behind a Cognito login, calls `DashboardApiFunction` same-origin — CloudFront injects the API key as a static origin header (never reaches the browser), and a Cognito ID token (from the dashboard's own login form) authorizes the actual request. See [README.md](README.md) for the file layout and commands.

## What this project is

An app that monitors a home solar + battery system by polling the SolaX Cloud API directly, storing the full usage history, and recommending optimised battery configuration options via a nightly assessment report — replacing the manual report exports currently used. Full context, including known site details, learnings from manual reports, and open questions, is in [docs/PowerPlant_Project_Brief.md](docs/PowerPlant_Project_Brief.md) — read it before starting implementation work.

## Commands

```bash
npm install && npm run install-all   # root deps + each lambda/*/'s own deps
npm test                              # jest — all specs in test/
npx jest test/tariff.test.js          # single test file (also: dashboard-api-function, alert-function, report-function, poller-function, battery-control-function, solax-client, infrastructure-stack, lambda-functions-stack, dashboard-stack)
npx cdk diff                          # preview changes against deployed stacks
npx cdk synth                         # synthesize CloudFormation templates (all stacks)
npm run deploy:dev                    # install + test + synth + deploy (scripts/deploy.sh, dev-powerplant.json)
bash scripts/deploy.sh --config dev-powerplant.local.json   # same, against the real/local config
```

CDK config (account, region, resource names, tags, SolaX device settings, tariff) lives in [config/dev-powerplant.json](config/dev-powerplant.json) (public template, placeholders only) — real values go in the gitignored `config/dev-powerplant.local.json`, loaded via `CDK_CONFIG=dev-powerplant.local.json` or `scripts/deploy.sh`'s `--config`/`-c` flag.

## Architecture

Three stacks, defined in [bin/powerplant.js](bin/powerplant.js):

1. **`PowerPlantInfrastructureStack`** ([lib/infrastructure-stack.js](lib/infrastructure-stack.js)) — stateful resources: a DynamoDB time-series table (`DeviceSn` partition key, `Timestamp` sort key, streams enabled), an SNS alerts topic, an SNS reports topic, a Cognito User Pool (gates the dashboard — see below), and the SolaX OAuth credentials as SSM `SecureString` parameters. Uses factory methods (`newDynamoDBTableFunction`, `newSNSTopicFunction`, `newCognitoUserPoolFunction`, `newSecureStringParameterFunction`) driven entirely by the config JSON — add a resource by adding a config block and a factory call, not by hand-writing CDK constructs inline.
2. **`PowerPlantLambdaFunctionsStack`** ([lib/lambda-functions-stack.js](lib/lambda-functions-stack.js)) — depends on stack 1, takes the table and topics as cross-stack references. Defines seven Lambdas via the same `newLambdaFunction` factory pattern (versioned + aliased):
   - `PollerFunction` — EventBridge `rate(5 minutes)` → calls SolaX Cloud for the Inverter device, plus the Battery device (auto-discovered via `getDeviceInfo` if `SOLAX_BATTERY_SN` isn't pinned in config) → writes one combined DynamoDB item per interval. Its role is granted `ssm:GetParameter`/`kms:Decrypt` on the SolaX SSM parameters via `grantSsmParameterRead` (by known ARN, not a live cross-stack reference — see below).
   - `DashboardApiFunction` — one Lambda, routes dispatched internally on `event.resource`/`event.httpMethod`: `GET /readings?range=day|week` (`aggregateReadings`, unchanged); `GET /insights` (`formatInsightsResponse` — the latest `ReportFunction` report record) and `POST /insights` (`handleTriggerAssessment` — asynchronously invokes `ReportFunction` with `{ sendEmail: false }`, see below); `GET /battery-status` (`formatBatteryStatusResponse` — the latest `BatteryControlFunction` decision record); `GET`/`PUT /battery-settings` (`formatBatterySettingsResponse`/`validateBatterySettings` — the dashboard-editable charge-%/on-off/dry-run override, see Battery charge control below); `GET`/`PUT /grid-discharge-settings` (`formatGridDischargeSettingsResponse`/`validateGridDischargeSettings` — the dashboard-editable enabled/dry-run override for `GridDischargeFunction`, see Grid discharge control below — note the PUT handler merges over the existing row rather than replacing it, since `SettingsOptimizerFunction` can also write other fields into the same row). The sentinel-prefixed GETs all share `queryLatestSentinelRecord` (`REPORT#`/`BATTERY_CONTROL#`/`BATTERY_CONTROL_SETTINGS#`) — see Dashboard insights persistence below.
   - `AlertFunction` — DynamoDB Stream event source (`INSERT` only). For each new reading it queries the immediately preceding reading (`grantReadData`, not just stream permissions) and runs two checks (`checkImportAnomaly`, `checkInverterFault`, both exported): an import-delta threshold outside the overnight `night-ev-charge` window, and the Inverter entering/changing a real fault state (`deviceStatus` 103 recoverable or 104 permanent — see `DEVICE_STATUS.INVERTER`). Publishes to the alerts SNS topic.
   - `ReportFunction` — `exports.handler = async (event) => {...}`; `event?.sendEmail !== false` gates the SNS publish (defaults `true` — a bare EventBridge invocation with no custom input, i.e. today's behavior, still emails). EventBridge nightly cron (`config.lambda.reportFunction.schedule`, sends email) plus an optional 6x/day refresh cron (`config.lambda.reportFunction.refreshSchedule`, `RuleTargetInput.fromObject({ sendEmail: false })` — refreshes the dashboard's `/insights` data without also sending 6 emails/day) and `DashboardApiFunction`'s `POST /insights` manual trigger (same `{ sendEmail: false }` payload, invoked via `Alias.grantInvoke`) all share this one flag rather than being separate code paths. Queries the last `REPORT_LOOKBACK_DAYS` (default 1) of readings, breaks import down by tariff window (`assessUsage`), and formats a plain-text report (`formatReport`) with a recommendation heuristic (both exported): if peak-window (`peak-evening`) import exceeds 0.5 kWh, recommends holding battery charge into that window rather than exporting earlier (feed-in 0.02 is far below the peak rate) — and when battery SOC data is available for the peak window specifically, differentiates "already depleted before peak started" (raise the charge target) from "ran flat during peak" (raise the discharge cutoff / capacity). When `config.bedrock.modelId` is set, also calls Bedrock for an AI narrative + pattern-based anomaly flags layered on top of that heuristic (`getAiInsights`, `dailySummaries`, `parseAiResponse`, all exported) — see AI insights below. Sends the email (if `sendEmail`), then best-effort writes the assessment as a record (`buildReportRecord`, exported) under `DeviceSn = REPORT#<inverterSn>` in the *same* readings table, every run regardless of `sendEmail` — see Dashboard insights persistence below. A failure on that write is logged and swallowed, never turns a successfully-sent report into a Lambda error.
   - `BatteryControlFunction` — nightly EventBridge cron, timed before the overnight grid-charge window. Reads a dashboard-editable settings override (`loadSettingsOverride`, sentinel `DeviceSn = BATTERY_CONTROL_SETTINGS#<inverterSn>`, fixed `Timestamp = 0`) and merges it over `config.batteryControl` (`resolveEffectiveSettings`, exported) — an unset override field, or no saved override at all, falls back to the static config value. When the merged `enabled` is `false`, skips the weather call and `classifyForecast` entirely (`classification` becomes the literal `'disabled'`) and instead resends the baseline with `chargeUpperSoc = disabledChargeUpperSoc` (default 100%, dashboard-editable) — the toggle turns off nightly *forecasting*, not the battery itself, so disabling it always converges the inverter on a known-safe default rather than leaving whatever the last forecast-driven decision set. Otherwise: fetches tomorrow's OpenWeatherMap forecast, classifies it (`classifyForecast`, exported), and resends `config.batteryControl`'s full self-use-mode baseline with only `chargeUpperSoc` varying (`buildSelfUseModeRequest`, exported) via `setInverterSelfUseMode` — the app's first control/write call, not just monitoring. Either way the result then goes through the same `dryRun`/live branch — `effective.dryRun` (also part of `resolveEffectiveSettings`'s merge, so dashboard-overridable independent of the `enabled` toggle) defaults `true` from `config.batteryControl.dryRun`, logging + emailing what it *would* do without calling SolaX. Before deciding, also calls `assessPreviousDecision` (exported, additive/Bedrock, same graceful-degradation pattern as `getAiInsights` — see Battery charge control below) to judge the *previous* stored decision against actual usage since; the result becomes `previousAssessment` on this run's record. Same best-effort persistence pattern as `ReportFunction`: writes `buildBatteryStatusRecord` (exported, takes a fields object) under `DeviceSn = BATTERY_CONTROL#<inverterSn>` at the end of every branch (disabled/dry-run/live). Skipped entirely if `config.ssm.weatherApiKey`/`config.location`/`config.batteryControl` aren't all present (backward-compat guard for older local configs). See docs/battery-charge-logic.md for the full decision logic and worked examples — **read that before ever setting `dryRun: false`.**
   - `GridDischargeFunction` — three EventBridge crons driving one Lambda, dispatched on `event.phase` (same pattern as `ReportFunction`'s `sendEmail`). Each phase handler starts by calling `loadSettingsOverride`/`resolveEffectiveSettings` (same fixed-key-row pattern as `BatteryControlFunction`, `DeviceSn = GRID_DISCHARGE_SETTINGS#<inverterSn>`) to resolve the effective `enabled`/`dryRun` — a dashboard override takes precedence, falling back to `config.gridDischarge.enabled`/`dryRun` when unset. `start` (5pm local) calculates how much battery capacity is genuinely surplus to the evening's load — from `minSoc` (`config.batteryControl.minSoc`, not duplicated in `config.gridDischarge`) plus the worst historical shoulder-night (9pm–midnight) reserve over the last `historyLookbackDays`, plus a safety margin — and discharges that surplus to the grid via VPP SOC Target Control (`setInverterSocTargetMode`) to capture a premium 5-9pm feed-in rate; `check` (7pm local, `config.gridDischarge.checkTime`) is the mid-window regulation step — `shouldExitEarly` (exported, unit-tested) checks for any grid import since the window opened (the one unambiguous signal that demand outpaced the discharge rate) or SOC already at/past the target, and if either is true, exits early via `exitVppMode` rather than waiting for `exit`; `exit` (9pm local) always calls Exit VPP mode (`exitVppMode`) to hand control back to `BatteryControlFunction`'s normal Self Use schedule, regardless of what `start`/`check` decided, since SOC Target Control has no built-in duration — idempotent if `check` already exited. `dryRun` defaults `true`, same safety pattern as `BatteryControlFunction`, and like `BatteryControlFunction` is now dashboard-overridable via a "Control mode" toggle pill (see the dashboard-editable settings bullet below). Skipped entirely if `config.gridDischarge`/`config.batteryControl` aren't both present. Writes `buildStatusRecord` under `DeviceSn = GRID_DISCHARGE#<inverterSn>` (one record per phase per run) — no GET dashboard route reads *that* yet, unlike `BATTERY_CONTROL#`, though `DashboardApiFunction`'s `POST /grid-discharge` (the dashboard's manual "Terminate discharge early" button) invokes the `exit` phase on demand, and `GET`/`PUT /grid-discharge-settings` (enabled/dry-run only, see below) does now exist. See [docs/grid-discharge-logic.md](docs/grid-discharge-logic.md) for the full calculation and worked example — **read that before ever setting `dryRun: false`.**
   - `SettingsOptimizerFunction` — weekly EventBridge cron (Sunday 22:00 Brisbane, deliberately after every other function's nightly schedule). Aggregates the last `lookbackDays` (default 7) of `BatteryControlFunction`'s (`BATTERY_CONTROL#`) and `GridDischargeFunction`'s (`GRID_DISCHARGE#`) own stored decision records — not raw readings — grouped by forecast classification (battery) and by shoulder-night reserve/early-exit-due-to-import events (grid discharge), and asks Bedrock whether `chargeUpperSocSunny`/`chargeUpperSocOvercast`/`gridDischarge.fallbackReservePercent`/`gridDischarge.safetyMarginPercent` should change. Two safety layers independent of what Bedrock returns: a `minSampleSize` gate (holds the current value if too few relevant nights exist) and a `maxAdjustmentPercent` clamp (bounds any recommendation to that many percentage points from the current value). `autoApply` defaults `false` — recommend-and-email only; when `true`, writes accepted recommendations into the same dashboard-editable settings-override rows `BatteryControlFunction`/`GridDischargeFunction` already read (`BATTERY_CONTROL_SETTINGS#`, and a new `GRID_DISCHARGE_SETTINGS#` added specifically for this — see the `GridDischargeFunction` bullet above), merging rather than replacing so an existing human-set `enabled`/`dryRun` toggle (either function's dashboard card writes both now) survives. Unlike `getAiInsights`/`assessPreviousDecision` (additive on top of a deterministic base), a Bedrock **call failure** here is a hard failure (throws, alarms) since the Bedrock assessment *is* this function's entire purpose — only an unparsable-but-successful response degrades gracefully to "no recommendation," matching `parseAiResponse`'s convention. Skipped entirely (not deployed) when `config.bedrock.modelId` isn't set. See [docs/settings-optimizer-logic.md](docs/settings-optimizer-logic.md) — **read that before ever setting `autoApply: true`.**
   - The `readings`/`insights`/`battery-status`/`battery-settings` API Gateway resources are exposed as `this.api` specifically so `DashboardStack` can reference it without a stack dependency cycle — see below.
   - `this.userPoolClient` — a Cognito app client (public, `generateSecret: false`) built via `new cognito.UserPoolClient(this, ..., { userPool, ... })`, **not** `userPool.addClient(...)`. That distinction matters: `addClient()` parents the resulting construct under the `userPool` scope regardless of which stack's code calls it, so it would silently land in `InfrastructureStack` instead of here — an easy, hard-to-notice mistake since everything still synths and grants correctly either way, just not where you'd expect. A `CognitoUserPoolsAuthorizer` (also created here) is attached to every method (GET/POST/PUT alike) alongside the existing API-key requirement — two independent layers, see Cognito authentication below.
3. **`PowerPlantDashboardStack`** ([lib/dashboard-stack.js](lib/dashboard-stack.js)) — depends on stack 2 only (the RestApi + the User Pool Client). Owns its own S3 bucket (deliberately *not* stack 1's — see below) plus a CloudFront distribution: default behavior serves the static `dashboard/` assets from that bucket (Origin Access Control), and `readings`/`insights`/`battery-status` cache behaviors (sharing one `RestApiOrigin`) forward to the API Gateway origin with the API key injected as a static origin header, so the browser-side JS never sees it. Also deploys a generated `config.json` (`s3deploy.Source.jsonData`, alongside the static asset source — not a secret, just the User Pool Client ID + region, needed because the client ID isn't known until the resource is actually created) so `app.js` knows what to talk to for login. Skipped entirely when `config.api.apiKeyValue` is still the `TODO_` placeholder (i.e. synth/deploy against the public template config).

Our own polling+storage is deliberate even though SolaX does expose a history endpoint (see below) — it gives an always-available time series with no retention/query-span limits, which both the dashboard and `ReportFunction`'s nightly recommendations depend on.

### Why the dashboard bucket isn't in `InfrastructureStack`

An Origin-Access-Control S3 bucket policy embeds the CloudFront distribution's own ARN in a condition, and the distribution's API origin needs the RestApi from `LambdaFunctionsStack` — so the bucket and the distribution must be co-located in one stack. Putting the bucket in `InfrastructureStack` (stack 1) while the distribution lives in `DashboardStack` (stack 3) creates a same-pair circular cross-stack reference (bucket policy needs the distribution's ARN, the S3 origin needs the bucket) regardless of which stack depends on which — CDK's `cdk synth` fails with a `DependencyCycle` error. `DashboardStack` therefore creates its own bucket via the same `config.s3.website` config block.

### SolaX API client (`lambda/Utilities/solax-client.js`)

Shared by all Lambdas via the `powerplant-shared` local package (`lambda/Utilities`, `main: index.js` re-exports `logger.js`, `solax-client.js`, and `tariff.js`). Built from [docs/solax-apis.md](docs/solax-apis.md), the full portal API reference including all 8 appendices (device type/model/status codes). `DEVICE_TYPE` (Appendix 3: Inverter=1, Battery=2, Meter=3, EV Charger=4, EMS=100) and `DEVICE_STATUS` (Appendix 6, the fault-relevant/common subset) are both exported and used directly by `PollerFunction`/`AlertFunction` — no more guessing at unconfirmed codes.

`solax-client.js` implements the **read/monitoring** endpoints (`docs/solax-apis.md` §1 Auth, §2 Information Management, §4 Monitoring Management), plus three control/write endpoints: §7 Inverter Work Mode Control's Self Use mode (`setInverterSelfUseMode`, `batch_set_spontaneity_self_use`), used by `BatteryControlFunction`; and §9 VPP Remote Control's SOC Target Control mode (`setInverterSocTargetMode`, `soc_target_control_mode`) plus Exit VPP mode (`exitVppMode`, `exit_vpp_mode`), used by `GridDischargeFunction` to discharge surplus battery capacity to the grid and hand control back afterward. Every other control/write endpoint (§3 EMS work modes, §6 export/import limits, §8 battery heating, the rest of §9 VPP remote control, §10 EV charger control, §11 A1-Hybrid-G2 modes) is still deliberately unimplemented — this app only monitors/recommends beyond those exceptions.

`getAccessToken` caches the Bearer token at module scope (reused across warm Lambda invocations); `PollerFunction` separately caches the Client ID/Secret it reads from SSM, and the discovered battery `deviceSn`, the same way.

### Battery device discovery (`PollerFunction.resolveBatterySn`)

The Battery device's `deviceSn` isn't a fixed, known-ahead-of-time value like the inverter's — `config.solax.batterySn` defaults to the placeholder `TODO_BATTERY_SN`. Whenever that env var is unset/still the placeholder, `PollerFunction` calls `getDeviceInfo({ deviceType: DEVICE_TYPE.BATTERY })` (no `plantId` needed — the account only has the one site) and caches the first result's `deviceSn` at module scope. Battery data is strictly a bonus on top of the required Inverter reading: `fetchBatteryReading` swallows its own errors and returns `null` rather than ever failing the whole poll, so a missing/undiscoverable battery just means that interval's DynamoDB item has no battery fields — every downstream consumer (`aggregateReadings`, `assessUsage`) checks for that and degrades gracefully.

### Tariff calculation (`lambda/Utilities/tariff.js`)

Pure functions shared by `DashboardApiFunction`, `AlertFunction`, `ReportFunction`, and `BatteryControlFunction`: `findImportRateWindow(tariff, timestampSeconds)` converts a UTC reading timestamp to local time via `Intl.DateTimeFormat` (no date library dependency) against `tariff.timezone` and matches it to a `[startTime, endTime)` window in `tariff.importRates`; `importCostForWindow` and `exportCredit` build on that. `localDateString(timestampSeconds, timezone)` (sortable `YYYY-MM-DD`, also `Intl.DateTimeFormat`-based) buckets readings/forecast slots into local calendar days — used by `ReportFunction.dailySummaries` and `BatteryControlFunction.fetchTomorrowForecastSlots`.

`tariff.timezone` isn't a field in `config.tariff` itself — a timezone describes the site being monitored, not the tariff structure, so it lives in `config.location.timezone` instead (alongside `lat`/`lon`, which `BatteryControlFunction`'s weather lookup also needs — one block, one source of truth, instead of two independently-set values that could drift out of sync). `LambdaFunctionsStack` builds the actual `TARIFF_STRUCTURE` env var as `JSON.stringify({ ...config.tariff, timezone: config.location.timezone })` once and reuses it for every Lambda that needs it. `config.location.timezone` defaults to `Australia/Sydney` in the public template — **still just an assumption for anyone else reusing this template**, wrong for any AU state that doesn't observe DST. The real site confirmed this is exactly that case: the local config uses `Australia/Brisbane` (fixed UTC+10, no DST) instead — this was a real, previously-flagged-but-unconfirmed bug, resolved once the site's actual location was known (see Battery charge control below).

### SolaX credentials via SSM (not Secrets Manager)

CloudFormation can't create `SecureString` SSM parameters natively, so `InfrastructureStack.newSecureStringParameterFunction` provisions them through an `AwsCustomResource` (`aws-cdk-lib/custom-resources`) calling `SSM PutParameter` directly. [bin/powerplant.js](bin/powerplant.js)'s `loadSolaxCredentials()` parses `solax-application-creds.txt` (gitignored, repo root) at synth time and passes the values in; if that file is absent (e.g. deleted after a successful seed), `InfrastructureStack` simply skips creating those two resources. The custom resources are `RemovalPolicy.RETAIN`, so removing them from a later synth (because the file's gone) does not delete the already-seeded parameter values — this is intentional, not a bug. `LambdaFunctionsStack` grants `PollerFunction`/`BatteryControlFunction` read access by reconstructing the parameter ARN from the config's `parameterName`, independent of whether `InfrastructureStack` actually (re-)created the resource this deploy. The OpenWeatherMap API key (`BatteryControlFunction`'s only external credential) follows the identical pattern — `loadWeatherApiKey()` parses `weather-api-key.txt` (gitignored) instead.

### Dashboard (`dashboard/`, served by `DashboardStack`)

A static single-page app (`index.html`/`app.js`/`styles.css`, no build step, Chart.js via CDN) — range toggle (day/week), summary cards, a bar chart, an insights section, and a weather/battery-decision widget pair, all sourced from `DashboardApiFunction`'s three routes. The energy rollup is a single aggregated object per range, not a time series, so the chart is one bar per metric rather than a trend line. All fetches go through `authorizedFetch` (see Cognito authentication below), which attaches the ID token and drops back to the login form on a 401/403.

### Dashboard insights + battery-status persistence

`/insights`, `/battery-status`, and `/battery-settings` all read from the *same* DynamoDB table the readings live in — no new data store. `ReportFunction` and `BatteryControlFunction` each write one record per run under a sentinel `DeviceSn` prefix (`REPORT#<inverterSn>` / `BATTERY_CONTROL#<inverterSn>`) that can't collide with a real device serial, and `DashboardApiFunction.queryLatestSentinelRecord` fetches the single newest one (`ScanIndexForward: false, Limit: 1`) for whichever prefix the route needs. `BATTERY_CONTROL_SETTINGS#<inverterSn>` is different in kind — a single fixed-key row (`Timestamp = 0`, not time-series) that a dashboard save upserts via `GetCommand`/`PutCommand` rather than a growing history — see Battery charge control below. This all reuses the table's existing partition/sort key schema and the Lambdas' existing table grants (`ReportFunction`/`BatteryControlFunction` need `grantReadWriteData`; `DashboardApiFunction` was upgraded from `grantReadData` to `grantReadWriteData` once `/battery-settings` needed to write) — no schema migration, no new table, no new stack resource.

The `REPORT#`/`BATTERY_CONTROL#` writes are best-effort (see the `ReportFunction`/`BatteryControlFunction` bullets above) — a DynamoDB hiccup never turns an already-sent email into a Lambda error, it just means the dashboard keeps showing the last successfully stored record (or `{ available: false }` if there's never been one yet). The `/battery-settings` write (a direct user action, not a background job) is the one place that *does* surface a failure straight back to the caller as an HTTP error, rather than degrading silently.

### Cognito authentication (dashboard login)

Two independent layers protect `/readings`, `/insights`, and `/battery-status`: the existing CloudFront-injected API key (protects the API from traffic that bypasses CloudFront) and a `CognitoUserPoolsAuthorizer` (protects the *data* — only someone who's actually logged in via the dashboard gets a response). No self-service sign-up (`selfSignUpEnabled: false`, `accountRecovery: NONE`) — this is a single-user personal app, so the one account is created post-deploy via `aws cognito-idp admin-create-user` + `admin-set-user-password --permanent` (see README) rather than provisioned in CDK with an embedded password.

`app.js` implements the login form with zero SDK — a plain `fetch` to `https://cognito-idp.<region>.amazonaws.com/` with `X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth` and `AuthFlow: USER_PASSWORD_AUTH`. This deliberately doesn't handle the `NEW_PASSWORD_REQUIRED` challenge — the setup instructions require a *permanent* password from the start (`admin-set-user-password --permanent`), so that challenge should never come up; if it does, `signIn()` surfaces a message pointing at the README rather than silently failing. The ID token (1 hour validity — `accessTokenValidity`/`idTokenValidity` on the `UserPoolClient`) is kept in `sessionStorage`, not `localStorage` (cleared when the tab closes) and never refreshed — `authorizedFetch` just drops back to the login form on expiry rather than implementing refresh-token rotation. This is a deliberately scoped-down v1: fully hiding the static HTML/JS shell (not just the data) would need Lambda@Edge/CloudFront Functions doing JWT validation at the edge, a meaningfully bigger addition — the shell itself is inert without a valid token, so this was judged not worth the extra cost/complexity for a single-user app.

### AI insights (`ReportFunction.getAiInsights`)

Additive, not a replacement for the deterministic `recommendation()` heuristic — Bedrock (`@aws-sdk/client-bedrock-runtime`, `InvokeModelCommand` against `config.bedrock.modelId`) is given today's `assessUsage()` output plus a day-by-day summary of the past `AI_HISTORY_LOOKBACK_DAYS` (default 14, via `dailySummaries` — deltas bucketed by local calendar day using `tariff.localDateString`, not raw 5-minute readings, to keep the prompt small). It's asked to return `{"narrative": string, "anomalies": string[]}` as JSON (`parseAiResponse` extracts the JSON even if the model wraps it in prose). Same graceful-degradation pattern as battery polling: no `modelId` configured, a Bedrock error, or an unparsable response all just mean the nightly report goes out without this section — never a failure. IAM grant is scoped to just that one model/inference-profile ARN.

`config.bedrock.modelId` is set to a specific Claude model ID in the local config (a Haiku-tier model — deliberately the cheaper/lighter tier rather than Sonnet, since this now runs up to 7x/day between the nightly cron and the 6x/day refresh below, not once) — **verify it's still available and enabled for your account/region in the Bedrock console** before relying on it; Bedrock's model catalog and per-region availability change over time. Confirmed for this deployment: plain base model IDs (`anthropic.claude-3-5-haiku-20241022-v1:0`, and even the older `anthropic.claude-3-haiku-20240307-v1:0`, which Bedrock now rejects as a "Legacy" model with no recent usage) are **not** invocable directly in `ap-southeast-2` — the local config uses the `au.anthropic.claude-haiku-4-5-20251001-v1:0` cross-region inference profile instead, verified working via a direct `bedrock-runtime invoke-model` test. `LambdaFunctionsStack.bedrockInvokeResources` grants `bedrock:InvokeModel` on both the profile ARN (this stack's own region) and the underlying foundation-model ARN with a **wildcard region** — cross-region profiles route the actual model call to whichever region within their geography serves it, which isn't necessarily this stack's region, so a same-region-only foundation-model grant would intermittently `AccessDenied`.

Runs more often than once/night now: the nightly cron (`config.lambda.reportFunction.schedule`, sends email) plus an optional 6x/day refresh cron (`config.lambda.reportFunction.refreshSchedule`, `sendEmail: false` — see the `ReportFunction` bullet above) keep the dashboard's `/insights` data closer to real-time than "up to ~24h stale," without turning into 6 emails/day. There's also a fully on-demand path: the dashboard's "Run assessment now" button → `DashboardApiFunction`'s `POST /insights` → `handleTriggerAssessment` asynchronously invokes `ReportFunction` (`InvocationType: 'Event'`, since the Bedrock call can run longer than API Gateway's 29s timeout) with the same `{ sendEmail: false }` payload. All three paths run the exact same handler code — the only variable is what triggered it and whether that run happens to send an email.

### Battery charge control (`BatteryControlFunction`)

The app's first control/write capability, not just monitoring — full decision logic, thresholds, and worked examples are in [docs/battery-charge-logic.md](docs/battery-charge-logic.md); this is a summary of what's structurally important:

- **No read-back endpoint.** `batch_set_spontaneity_self_use` is a full-replace write (`minSoc`, `chargeFromGridEnable`, `chargeUpperSoc`, all four charge/discharge time-window fields, `enableTimePeriod2`) with no corresponding "get current settings" endpoint anywhere in `docs/solax-apis.md`. `config.batteryControl` therefore holds the household's actual current settings (captured once from the SolaX app) as this app's source of truth, resent in full every call — only `chargeUpperSoc` varies, decided nightly by `classifyForecast`. **If the SolaX app's settings are ever changed manually after this goes live, `config.batteryControl` needs updating and redeploying to match, or the next run silently reverts them.**
- **Endpoint choice**: targets the Inverter-level endpoint (`chargeUpperSoc`), not the EMS System endpoint (`chargeCutOffSoc`, `ems_system/control/work_mode/self_use`) that requires EMS1000/EMS1000 PRO firmware — this system has no EMS device (only Inverter + Battery, same as everywhere else in this app).
- **Weather**: OpenWeatherMap's free 5-day/3-hour forecast endpoint (`/data/2.5/forecast`), filtered to whichever 8 slots fall on tomorrow's local date (`localDateString`, see Tariff calculation above). `config.location.lat`/`lon` are the real site coordinates — gitignored-local-config-only, same sensitivity tier as the inverter serial/AWS account ID. `config.location` also holds `timezone`, shared with the tariff-window matching above — one config block for everything that describes "where the site is."
- **Safety**: `config.batteryControl.dryRun` defaults `true` in both configs — always logs + emails what it *would* do; only calls the real SolaX endpoint when a resolved `dryRun` of `false` is in effect (config default or a dashboard override, see below). Any failure publishes to the alerts topic and lets the Lambda error (so `BatteryControlFunctionErrorAlarm` fires).
- Runs nightly at 21:30 Brisbane time (`cron(30 11 * * ? *)`, fixed since Queensland has no DST) — before the 00:00–06:00 overnight grid-charge window starts, and deliberately *after* `GridDischargeFunction`'s 9pm exit phase (see Grid discharge control below) rather than the original 20:00, which overlapped the 5-9pm discharge window and risked the two Lambdas fighting over control of the inverter.
- **Dashboard-editable settings**: `chargeUpperSocSunny`/`chargeUpperSocOvercast`/`disabledChargeUpperSoc`/`enabled`/**`dryRun`** can be overridden from the dashboard (`GET`/`PUT /battery-settings`) without a redeploy — `loadSettingsOverride`/`resolveEffectiveSettings`, see the `BatteryControlFunction` bullet above. `enabled: false` skips forecasting for that run and instead holds `chargeUpperSoc` at `disabledChargeUpperSoc` (default 100%) every night until re-enabled — independent of `dryRun`. The dashboard's "Battery Control Settings" panel renders `enabled` and `dryRun` as toggle-pill switches (`dashboard/styles.css`'s `.toggle-pill`/`.toggle-pill--danger`) rather than a plain checkbox — the dry-run/live pill is the danger variant (turns red when live) and its dashboard change handler (`dashboard/app.js`) requires a `confirm()` before it can be switched on, since flipping it now takes effect on the very next nightly run with no redeploy required — see docs/battery-charge-logic.md's "Dashboard-editable settings" for the safety implications of that. `minSoc`/time windows/`chargeFromGridEnable` are *not* dashboard-editable — still config-only.
- **Previous-decision accuracy assessment**: `assessPreviousDecision` (additive, Bedrock, same `config.bedrock.modelId`/graceful-degradation pattern as `getAiInsights`) judges the last stored decision against actual usage since (`summarizeUsage` — PV/import/export deltas + battery SOC range), stored as `previousAssessment` on the new record. Shown on the dashboard as a "Last night's accuracy" widget.

### Grid discharge control (`GridDischargeFunction`)

The app's second control/write capability — deliberately *exporting* battery charge, not just self-consuming through it. Full calculation, worked example, and known risks are in [docs/grid-discharge-logic.md](docs/grid-discharge-logic.md); summary of what's structurally important:

- **The arbitrage**: a retailer feed-in rate of 27c/kWh applies 5-9pm (`config.gridDischarge.peakFeedInRate`/`windowStartTime`/`windowEndTime`) — well above the flat 2c/kWh feed-in rate the rest of the day. Self-consumption still avoids more (the 41.756c/kWh peak import rate) than exporting earns, so this never discharges further than the evening's load needs — it only exports the charge that would otherwise sit idle until the next overnight recharge anyway.
- **No read-back, and no built-in duration either**: like `batch_set_spontaneity_self_use`, VPP SOC Target Control has no "get current settings" endpoint — but unlike Self Use mode, it also has no time-window/duration field at all. The inverter holds in VPP override indefinitely once set, so a separate `exit` phase (Exit VPP mode) is the *only* thing that hands control back to `BatteryControlFunction`'s normal Self Use schedule — see the `GridDischargeFunction` bullet above for why it's always attempted regardless of what `start` decided.
- **Target calculation is historical, not forecast-based** (unlike `BatteryControlFunction`'s weather-driven `chargeUpperSoc`): looks back over `historyLookbackDays` local calendar days at the shoulder-night (9pm-midnight) SOC drop, uses the **worst** night (not average), and falls back to a static `fallbackReservePercent` (26%, grounded in a real week of SolaX plant-report data — see docs/grid-discharge-logic.md) when fewer than `minHistoryDaysRequired` nights have usable *live* data — every fallback in the calculation resolves toward holding *more* charge, never less. Distinct from — and doesn't cover — the 6am-9am pre-solar morning gap, which is `BatteryControlFunction`'s `chargeUpperSoc` sizing's job, not this function's.
- **`minSoc` is shared, not duplicated**: reads `config.batteryControl.minSoc` (the same protected floor `BatteryControlFunction` uses) rather than its own copy — merged into the `GRID_DISCHARGE_CONFIG` env var at deploy time, same pattern as `TARIFF_STRUCTURE` merging in `config.location.timezone`.
- **The `GRID_DISCHARGE_SETTINGS#<inverterSn>` row (`GridDischargeFunction.loadSettingsOverride`/`resolveEffectiveSettings`, same fixed-key-row pattern as `BatteryControlFunction`'s `BATTERY_CONTROL_SETTINGS#`) has two independent writers.** The dashboard's "Grid Discharge Control" card writes `enabled`/`dryRun` (`GET`/`PUT /grid-discharge-settings`, `DashboardApiFunction.handleGetGridDischargeSettings`/`handlePutGridDischargeSettings`) — rendered as the same `.toggle-pill`/`.toggle-pill--danger` switches as the battery-settings card, dry-run/live confirm-gated the same way. `fallbackReservePercent`/`safetyMarginPercent` are *not* dashboard-editable — `SettingsOptimizerFunction` (see below) is their only writer, and only when `autoApply: true`. Because the PUT handler only ever knows about `enabled`/`dryRun`, it reads the row first and merges those two fields on top rather than replacing the item outright, so it never clobbers a `fallbackReservePercent`/`safetyMarginPercent` the optimizer already set.
- **Safety**: `config.gridDischarge.dryRun` defaults `true` in both configs, same pattern as `BatteryControlFunction`. Any failure (either phase) publishes to the alerts topic and lets the Lambda error (so a `GridDischargeFunctionErrorAlarm` fires).
- Runs at 5pm (`start`), 7pm (`check`), and 9pm (`exit`) Brisbane time, three fixed crons (`cron(0 7 * * ? *)`/`cron(0 9 * * ? *)`/`cron(0 11 * * ? *)`, no DST).
- **Mid-window regulation (`check` phase, `shouldExitEarly`, exported/unit-tested)**: answers "what if demand is higher than normal" — rather than inferring trouble from how fast SOC is falling (ambiguous — could just mean the target was reached early, which is fine), it checks for the one unambiguous bad signal directly: any grid import since the window opened. Import detected, or SOC already at/past the target, both trigger the same corrective action — call `exit_vpp_mode` immediately instead of waiting until 9pm. Deliberately a single check, not continuous monitoring — the window is short and a modest amount of over-discharge past the target is an accepted cost; see docs/grid-discharge-logic.md's "How discharge is regulated mid-window".
- **Manual termination**: the dashboard's "Grid Discharge Control" section has a "Terminate discharge early" button (`POST /grid-discharge`, Cognito-protected, `DashboardApiFunction.handleTriggerGridDischargeExit`) that invokes the same `exit` phase on demand (`InvocationType: 'Event'`, same fire-and-forget pattern as `POST /insights`) — not new logic, just an on-demand trigger for the existing always-safe exit path. Safe to press even when nothing is running.
- **Dashboard-editable settings**: the same card also has an "Evening discharge enabled" toggle and a "Control mode" (dry-run/live) toggle, same `.toggle-pill`/`.toggle-pill--danger` component and confirm-before-live pattern as `BatteryControlFunction`'s card (see Battery charge control above) — `GET`/`PUT /grid-discharge-settings`, backed by `GridDischargeFunction`'s `GRID_DISCHARGE_SETTINGS#<inverterSn>` row. Unlike battery-settings, the PUT handler here merges (`{...existing, enabled, dryRun}`) instead of replacing the item, since `SettingsOptimizerFunction` can independently write `fallbackReservePercent`/`safetyMarginPercent` into the same row.
- **No read/status dashboard visibility yet** — writes `GRID_DISCHARGE#<inverterSn>` status records the same way `BatteryControlFunction` writes `BATTERY_CONTROL#<inverterSn>` (one per phase per day: `start`/`check`/`exit`), but `DashboardApiFunction` doesn't expose a GET route for them (only the manual-termination POST exists so far). Validate dry-run output via the reports-topic email and CloudWatch Logs for now.
- **Known gap**: `ReportFunction`'s cost assessment still values *all* export at the flat `config.tariff.feedInRate` — it doesn't yet know about the 5-9pm premium rate, so nightly reports understate the value of anything this function exports. `tariff.js`'s `exportCredit` would need a time-varying rate structure (mirroring `importRates`) to fix that — not yet done.
- **Known gap**: whether VPP SOC Target Control is load-preserving (battery serves load first, only true surplus exports) or a literal fixed-rate command (grid fills any shortfall vs. commanded rate) is unconfirmed from `docs/solax-apis.md` alone — the single biggest open risk, more fundamental than the mid-window check above. Resolve before ever setting `dryRun: false` — see docs/grid-discharge-logic.md's "Known risks".

### Settings optimizer (`SettingsOptimizerFunction`)

The app's first *self-tuning* capability — every other decision function (`BatteryControlFunction`, `GridDischargeFunction`) has static config defaults a human sets once; this one periodically asks whether those defaults still look right. Full logic, worked example, and known risks are in [docs/settings-optimizer-logic.md](docs/settings-optimizer-logic.md); summary of what's structurally important:

- **A rollup of other functions' judgements, not an independent check** — aggregates `BatteryControlFunction`'s nightly `previousAssessment` accuracy calls and `GridDischargeFunction`'s stored `shoulderNightReservePercent`/early-exit-due-to-import events over `lookbackDays` (default 7), and asks Bedrock whether `chargeUpperSocSunny`/`chargeUpperSocOvercast`/`gridDischarge.fallbackReservePercent`/`gridDischarge.safetyMarginPercent` should move. If those upstream judgements are wrong, this function propagates that, it doesn't catch it.
- **Two safety layers independent of the AI response**: a `minSampleSize` gate (holds the current value if too few relevant nights exist for that specific setting) and a `maxAdjustmentPercent` clamp (bounds any surviving recommendation to that many percentage points from the current effective value, and to `[0, 100]`) — enforced in code (`buildRecommendations`), not left to the model's own restraint.
- **`autoApply` defaults `false`** (recommend-and-email only) in both configs, same dry-run-first posture as every other control function here, just named differently since there's no separate live/dry external call to gate — the only "live" action is the settings-override write itself. When `true`, writes merge into (never replace) the existing `BATTERY_CONTROL_SETTINGS#`/`GRID_DISCHARGE_SETTINGS#` rows, so an existing human-set toggle like `enabled`/`dryRun` survives.
- **A Bedrock call failure is a hard failure here**, unlike `getAiInsights`/`assessPreviousDecision` — this function has no deterministic base to fall back to, the Bedrock assessment *is* the whole point, so a failed call throws (alarms) rather than degrading silently. An unparsable-but-successful response still degrades gracefully to "no recommendation," matching `parseAiResponse`'s existing convention.
- Runs weekly, Sunday 22:00 Brisbane (`cron(0 12 ? * SUN *)`) — deliberately after every other function's nightly schedule, so any change takes effect starting the next day, never mid-flight. Skipped entirely (not deployed at all, unlike the additive AI features) when `config.bedrock.modelId` isn't set.

Build phases per the project brief: (1) ingest — done, both Inverter and Battery devices, (2) dashboard — done, `DashboardApiFunction` plus a static S3+CloudFront frontend, (3) cost tracking — done, (4) alerts — done, real fault codes, (5) nightly assessment & recommendations — done, SOC-aware when battery data is present, optionally enriched with Bedrock-generated narrative/anomalies, (6) automated battery charge control — implemented, dry-run by default pending validation against real forecasts (see docs/battery-charge-logic.md), (7) grid discharge arbitrage — implemented, dry-run by default pending validation against more shoulder-night history (see docs/grid-discharge-logic.md), (8) settings optimizer — implemented, recommendation-only by default pending validation against real weekly history (see docs/settings-optimizer-logic.md).

## SolaX Cloud API integration notes

- **Base URL**: `https://openapi-eu.solaxcloud.com` (this account's region). **Auth**: `POST /openapi/auth/oauth/token`, Client ID/Secret → Bearer `access_token`, ~30 day expiry, doesn't extend on use (re-call to refresh).
- **Real-time telemetry**: `GET /openapi/v2/device/realtime_data`, `snList` (device serials) + `deviceType` + `businessType` (`1` = Residential). This resolved the earlier open question — real-time data lives on this same OpenAPI platform, not the older `tokenId`-based `dataAccess/realtimeInfo` endpoint the project brief originally assumed.
- **History endpoint does exist** (`GET /openapi/v2/device/history_data`, ≤1 year range, ≤12h query span, 5/10/15/30/60 min intervals) — another original assumption ("no historical query endpoint") was wrong. We still poll-and-store ourselves rather than rely on it (see Architecture above).
- **`deviceType` (Appendix 3, all confirmed)**: `1` Inverter, `2` Battery, `3` Meter, `4` EV Charger, `100` EMS.
- **`deviceStatus` (Appendix 6, confirmed for Inverter/Battery/EV Charger)**: Inverter fault states are `103` (recoverable) and `104` (permanent) — everything else in the (large) enum is a normal operating/mode state, not a fault, so `AlertFunction` only checks for those two. Residential batteries only ever report `0` (Idle) / `1` (Work) — no fault states exist there.
- Rate limit context: a 5-minute polling schedule is 288 calls/day, plus an occasional battery-discovery call — comfortably inside whatever quota applies to this endpoint family.
- Real credentials for the OAuth flow are in `solax-application-creds.txt` at the repo root (gitignored) — never commit it. Runtime credential storage is SSM Parameter Store (`SecureString`), not Secrets Manager — see above. The OpenWeatherMap API key follows the same pattern via `weather-api-key.txt`.
- **§7 Inverter Work Mode Control**: `batch_set_spontaneity_self_use`, via `BatteryControlFunction` — see Battery charge control above and `docs/battery-charge-logic.md` for the full picture, including why there's no way to read the inverter's current work-mode settings back.
- **§9 VPP Remote Control**: `soc_target_control_mode` + `exit_vpp_mode`, via `GridDischargeFunction` — see Grid discharge control above and `docs/grid-discharge-logic.md`. Note the `chargeDischargPower` sign convention here is +charge/-discharge, the *opposite* of the Push Power VPP modes' `batteryPower` (+discharge/-charge) — easy to get backwards.
- `docs/solax-apis.md` is the working reference — it's now complete (all appendices included), so any field/endpoint not in it genuinely isn't part of this API rather than just undocumented.
